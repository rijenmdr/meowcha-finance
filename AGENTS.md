# Meowcha Finance Dashboard

A single-admin finance dashboard for a small bookbinding business. It covers transactions, budgets, invoices, customers and categories. Amounts are in Nepali Rupees (`Rs`, lakh/crore grouping).

## Stack

- **Next.js 16** (App Router) with **React 19** and **TypeScript** in strict mode
- **Supabase Auth**: email/password sign-in with server-side session checks and a single admin account
- **Supabase** (Postgres) through `@supabase/supabase-js`, used **only on the server** with the service role key
- **@supabase/ssr** for browser sign-in and cookie-based session refresh
- ESLint 9 flat config (`eslint-config-next` core-web-vitals + typescript)
- **Tailwind CSS v4** (`@tailwindcss/postcss`): utility classes only, with design tokens in `globals.css` `@theme`
- **shadcn/ui** (`radix-nova` style, Radix primitives, `lucide-react` icons): component source lives in `src/components/ui`, restyled to the brand

## Commands

```bash
npm run dev     # start dev server (also regenerates the block at the top of this file)
npm run build   # production build — run this to type-check
npm run lint    # eslint
```

There is no test suite yet.

## Architecture and data flow

1. **Auth gate.** `src/proxy.ts` sends unauthenticated requests to `/login`. `(dashboard)/layout.tsx` checks the Supabase user again as defense in depth. Keep both checks.
2. **Reads.** The browser never receives whole tables or computes totals. Filtering, aggregating and paging happen in Postgres, in the reporting functions at the end of `supabase/schema.sql` (`overview_summary`, `list_transactions`, `list_orders`, `customer_summary`…, all returning jsonb). Income totals read the `report_transactions` view, which takes outside-provider delivery charges off delivered orders' payments.
   - The dashboard layout (`dynamic = "force-dynamic"`) loads only the small **lookup tables** (`getLookups()`: categories, channels, sources, customers, providers, methods, products, budgets) inside a `<Suspense>` boundary (`DashboardContent`) and passes them to `LookupsProvider`. TopNav and Sidebar stream first and `DashboardSkeleton` fills the content area until they arrive. `LookupsProvider` is the app's only React context: the lookups are server data, so they never go in a store.
   - Each **page is a server component** that only parses params, calls one `getXPage()` loader from `lib/queries/`, and renders one `<XContainer data={data} />`. The loader calls one SQL function and formats display-ready rows (`fmtMoney`, status classes). Containers are server components that render small `"use client"` children (tables, filters, editors). `(dashboard)/loading.tsx` shows `PageSkeleton` while a page loads.
   - Transactions, orders and invoices are **paginated on the server** (`useServerDataTable`, `?page=&size=&sort=&dir=`). The smaller lists arrive whole and page in the browser (`useDataTable`).
3. **Client state.** Only UI state lives on the client, in small Zustand stores: `use-dialog-store` (the open dialog and the record being edited, passed in from the row that opened it), `use-confirm-store` (`confirm()` / `notify()`, rendered by `ConfirmDialog`) and `use-navigation-store` (pending URL navigations, which `ContentFrame` uses to dim the page). `useLookups()` gives dialogs their dropdown options and editing records. `useUrlSearch().setSearch()` changes URL params inside a transition; `useDateFilter()` drives the Header's period controls.
4. **Writes.** Every server action calls `refresh()` (from `next/cache`) after it succeeds, so the server re-renders the page with fresh totals. There is no client-side copy of records to keep in sync. Dialog submits (`useSubmitX()`) `await` the action, then close the dialog, so a failed save leaves the dialog open with an error. Deletes, `markInvoicePaid` and order status steps are **optimistic**: each table's `useXRows(rows)` (built on `useOptimisticRows`) hides or patches the row until the action and its refresh land, and the row reverts if the action fails. New IDs come from `newId()` (`crypto.randomUUID()`) on the client.
5. **Server actions.** Every action in `lib/actions/` must:
   - call `requireSession()` (from `lib/supabase/auth.ts`) first
   - send the input through a `parseX()` from `lib/validators/`, because action arguments are untrusted and TS types are not enforced at runtime
   - map camelCase fields to snake_case columns
   - `throw new Error(error.message)` on a Supabase error
   - call `refresh()` after the write succeeds
6. **Dialogs.** One `DialogHost` renders the active dialog based on the dialog store's `dialog` (`DialogKind`) and `editId`. It is keyed by `dialog-editId` so uncontrolled forms (`defaultValue`) reset. `DialogOverlay` owns the submit lifecycle: it passes `FormData` to the dialog's `onSubmit`, disables the fields in a `<fieldset>` and shows "Saving…" while the returned promise is pending. It also renders the Cancel/Save buttons and the error message.

### Adding a new entity (checklist)

1. Add the table to `supabase/schema.sql` with RLS enabled and **no policies**. If existing databases need converting, add a numbered script to `supabase/migrations/`.
2. Add the types to `models/<entity>.ts` (entity, `XSubmitValues`, table row), any allowed values to `enums/`, and a `DIALOG_KIND` member if it needs a dialog.
3. Add `lib/queries/<entity>.ts`. A small reference table gets `getX()` (map snake_case → camelCase), included in `getLookups()`. Put its totals or paged list in a SQL function in `schema.sql` plus a migration (revoke execute from `public, anon, authenticated` and grant it to `service_role`), and add a `getXPage()` loader.
4. Add `parseX()` to `lib/validators/<entity>.ts`, then `saveXAction` / `deleteXAction` to `lib/actions/<entity>.ts`.
5. Add `hooks/mutations/use-<entity>-mutations.ts` (`useSubmitX`, `useXRows`), and dropdown options to `hooks/use-lookups.ts` if it appears in dropdowns.
6. Add `components/containers/<route>/<route>-container.tsx` and `<route>-table.tsx`, and `components/shared/dialogs/<entity>-dialog.tsx` registered in `DialogHost`. Add the route under `(dashboard)/`, its title and add button to `constants/page-header.ts`, and its link to `constants/navigation.ts`.

## Naming conventions

| Thing | Convention | Example |
| --- | --- | --- |
| Files and folders | kebab-case everywhere; one exported component per file (`components/ui/` keeps shadcn's several exports per file) | `invoices-table.tsx`, `use-order-form.ts` |
| Components | Named exports (`export function X`) — **no default exports** | `export function Panel` |
| Route pages/layouts | `page.tsx` / `layout.tsx` with a default export | `export default function InvoicesPage` |
| Route folders | lowercase, kebab-case if multi-word | `transactions/` |
| Page entry components | `<route>-container.tsx` / `XContainer`; the only files with that suffix | `orders-container.tsx` |
| Entity files | singular: `lib/actions/order.ts`, `models/order.ts` | `lib/queries/customer.ts` |
| Hooks / stores | `use-` prefix; stores end in `-store` | `use-dialog-store.ts` |
| Table / list components | plural noun + `Table` | `CustomersTable` |
| Dialog components | singular noun + `Dialog` (`Txn` for transactions) | `TxnDialog`, `BudgetDialog` |
| Server actions | `saveXAction`, `deleteXAction` (verb + entity + `Action`) | `saveInvoiceAction` |
| Data loaders | `getX` (plural); per-page loaders `getXPage` | `getInvoicesPage` |
| Validators | `parseX` | `parseInvoice` |
| Types | PascalCase interfaces; form types `XFormValues`, submit payloads `XSubmitValues` | `InvoiceSubmitValues` |
| Enums | `as const` object + union type, never TS `enum` | `ORDER_STATUS` / `OrderStatus` |
| Constants | SCREAMING_SNAKE_CASE | `ACCENT_RAMP`, `ORDER_STATUS_CLASSES` |
| Shared class strings | camelCase + `Class` suffix, exported from the owning component | `textButtonClass` |
| DB tables / columns | plural snake_case tables and snake_case columns; camelCase in TS | `issue_date` ↔ `issueDate` |
| Dates | `YYYY-MM-DD` strings throughout, never `Date` objects in state | `"2026-09-15"` |
| References | Always link to another record by id with a real foreign key, never by name. Join names in the SQL reporting functions (or look them up in `useLookups` for forms) | `categoryId` / `category_id` |

## Code style

- Import from `src/` with the `@/` alias across folders (`@/lib/…`, `@/components/…`). Use relative `./` imports inside the same folder.
- Put `"use client"` only on the smallest component that needs hooks or events. Containers and presentational components such as `Panel` stay server components.
- Server-only modules start with `import "server-only";`. Never import `lib/queries`, `lib/validators`, `lib/supabase/server.ts`, `rpc.ts` or `auth.ts` from client code (`import type` is fine).
- Dependency direction: `ui/` imports nothing from `shared/` or `containers/`; `shared/` never imports `containers/`; a route's container folder never imports another route's; `lib/helpers` and `lib/utils` never import React, Supabase or `lib/actions`.
- Use `import type` for type-only imports.
- Keep comments rare and use them to explain *why*, like the existing ones.
- Put aggregation (sums, counts, grouping, paging) in SQL, not TypeScript. Put the remaining pure logic in `lib/helpers` (domain) or `lib/utils` (generic), and stateful UI logic in `hooks/`, not in components.
- Soft limits: ~150 lines per component file, ~40 lines per function, 5 or fewer props, no nested ternaries.
- Use `fmtMoney` / `fmtDate` for every displayed amount and date. Never format by hand.

## Styling

- Use Tailwind utility classes and never `style={{…}}`. Do not add CSS modules or another component library without asking. Read the `tailwind-css` and `shadcn` skills in `.claude/skills/` before styling work.
- Build UI from the shadcn primitives in `@/components/ui` (`Button`, `Input`, `NativeSelect`, `Field`, `Table`, `Badge`, `Dialog`, `AlertDialog`, `Skeleton`…) before writing raw elements. Pick a variant (`variant="outline"`, `size="icon-sm"`) before adding classes, and use `className` for layout only.
- Add new primitives with `npx shadcn@latest add <name>`, then bring them onto the brand: replace `text-xs/sm/base/lg` with `text-12/14/15/17`, drop `rounded-*`, change `import { cn } from "cn"` to `@/lib/utils/cn`, and remove any `style={{…}}`.
- Use theme tokens from `globals.css`: `bg-canvas`, `bg-surface`, `text-ink` (faded `text-ink/60`), `border-line` / `border-line-soft`, `accent-50…800` (`accent-500` = `#7f8051`, olive), `graphite`, `mist`, `text-error`. shadcn's semantic tokens (`bg-primary`, `bg-muted`, `text-muted-foreground`, `bg-accent`, `border-input`, `ring-ring`, `text-destructive`) are mapped onto that palette in `:root`, so either kind of token is on-brand. Note that `accent-500` is the olive scale and bare `bg-accent` is shadcn's hover tint. Font sizes are px-named (`text-13`) and the default `text-sm`/`text-lg` scale is removed. Every radius is pinned to 0.
- Fonts: `font-sans` (Barlow) for body text and `font-condensed` (Barlow Condensed) for headings, titles and buttons.
- Derived display data returns full class strings (`amountClass`, `statusClass`), never hex values, and never builds class names from fragments. Join classes with `cn()` from `@/lib/utils/cn`. Never import `cn` from the `cn` package directly, because the default merger reads `text-13` as a color and drops it.
- Build panels from `Panel` + `CornerBrackets` (both take `className`). Dialogs render through `DialogOverlay` (a shadcn `Dialog`, which owns the title, footer buttons and submit lifecycle) with `Field` + `FieldLabel` + a control for each input. Confirmations and alerts use `confirm()` / `notify()` from `stores/use-confirm-store.ts` (rendered by `ConfirmDialog`), never `window.confirm`/`window.alert`.

## Security

- `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS, so it must never reach the client and must never get a `NEXT_PUBLIC_` prefix.
- RLS stays **enabled with no policies** on every table.
- Every server action checks the session and validates its input, with no exceptions.
- Security headers live in `next.config.ts`. Keep `frame-ancestors 'none'` / `X-Frame-Options: DENY`.
- Use the `owasp-security` skill in `.claude/skills/` for security reviews.

## Gotchas

- Get "today" from `todayISO()` in `lib/utils/date-math.ts`, never `new Date()`. It reads the date in Nepal time (`Asia/Kathmandu`), so the server render and the browser agree. Date math (`addDays`, `monthKeysBetween`) works in UTC on `YYYY-MM-DD` strings, because `toISOString()` on a local-midnight `Date` lands on the previous day east of UTC.
- The date filter lives in the URL (`?period=today|week|month|year|custom&from=…&to=…`), defaults to today, and is written with `router.replace` (through `setSearch`), so the page re-renders on the server for the new range. Changing it drops `?page`. Links between dashboard pages carry it along with `pickDateFilterSearch` / `withDateFilter`.
- `customerId` is optional on invoices and income transactions, and always `null` on expenses. Deleting a customer unlinks those records (`on delete set null`) instead of deleting them. On orders `customerId` is **required**, so deleting a customer who has orders fails at the DB. `deleteCustomer` checks first and shows an alert.
- A transaction's `type` must match its category's type (and its channel's, when set). The composite FKs `(category_id, type) → categories (id, type)` and `(channel_id, type) → channels (id, type)` enforce this.
- `channelId` is optional on every transaction. Deleting a channel unlinks its transactions (`on delete set null (channel_id)`) instead of failing like a category.
- `sourceId` (where an expense's money came from) is optional and only valid on expenses: `sources.type` is pinned to `'expense'` and the composite FK `(source_id, type) → sources (id, type)` rejects it on income. Deleting a source unlinks its expenses (`on delete set null (source_id)`).
- A product has `option_names` (e.g. Color, Type) and many `product_variants`. Each variant has its own `options` jsonb (unique per product), `price` and `quantity`. Order items reference a **variant** (`order_items.variant_id`), never the product. `save_product(p_product, p_variants)` writes a product and replaces its variants atomically, and removing a variant that is on an order fails at the DB, so the client checks first.
- Deleting a category that is still in use fails at the DB. The client checks first and shows an alert (`deleteCategory`).
- **Product categories** (`product_categories`, the `/product-categories` page) are separate from the transaction `categories`. Every product has exactly one (`products.category_id`, required, `on delete restrict`), so deleting a category that still has products fails at the DB and `deleteProductCategory` checks first. Migration `019` filed all earlier products under a "Journal" category, which is an ordinary category. The Products page filters by `?category=<id>` through `product_summary(p_category_id)`, which narrows the stock totals as well as the rows.
- An order and its `order_items` are saved together by the `save_order(p_order, p_items, p_payment)` Postgres function (an RPC), so the write is atomic. It replaces every item on each save. `orders.sub_total` is the sum of the item sub-totals, and `total_price` and `payment_status` are generated columns, so never write them directly. `orderTotals()` in `lib/helpers/order-totals.ts` does the same math on the client. The DB assigns `order_number` (`ORD-0001`…) from a sequence on first insert, and a trigger keeps it from changing. `save_order` returns the number, and `saveOrderAction` passes it back to the client.
- Order payments are income transactions with `transactions.order_id` set, and only income rows may have one. `orders.amount_paid` is **never written directly**. A trigger on `transactions` keeps it equal to the sum of the order's payments, so editing or deleting a payment on the Transactions page changes the order. An order's **advance** (`transactions.is_advance`, at most one per order) is the payment the order editor creates and edits: `save_order`'s `p_payment` inserts it the first time and updates it on every later save, and `null` leaves it alone (remove one on the Transactions page). Later payments go through `add_order_payment` (`recordOrderPaymentAction`, the Record payment dialog). Payment descriptions come from SQL. Deleting an order keeps its payments as unlinked income, and a trigger clears `is_advance` on any payment that loses its `order_id`.
- **Requests** are orders with `order_status = 'requested'` (made to order), listed on the Orders page's Requests tab (`?tab=requests`, `list_orders`' `p_tab`). The Requests tab ignores the date filter. `requested` is only set on create and is left by conversion (the editor's Convert mode, to `processing`) or by cancelling. A request holds only its advance, so `add_order_payment` rejects it. `orders.requested_date` is set on create and kept after conversion ("From request"). A request's items are saved with `stock_tracked = false` and never touch stock, even after conversion. The `guard_order_status` trigger enforces the status moves.
- **Cancelling** (`cancel_order`, `cancelOrderAction`) is allowed from `requested`, `processing` and `ready_for_delivery` (`CANCELLABLE_STATUSES` in `constants/order-status.ts` and the same list in SQL). It puts stock-tracked items back and marks them untracked, so a later delete doesn't restore them twice. A cancelled order is read-only (the editor's `view` mode) but can still be deleted, and its payments stay as income. Requested and cancelled orders are left out of the Orders tab totals and the provider/method in-range totals, but stay in every `order_count`.
- An outside provider's delivery charge only comes off an order's payments in `report_transactions` once the order is `delivered`. Until then the payments count as income in full, so marking an order delivered lowers income on the original payment dates.
- `deliveryProviderId` and `paymentMethodId` are optional on orders. Both are columns on `orders`, written by `save_order`, so a new order column means updating `save_order` in `schema.sql` and in a migration. Deleting a provider or method unlinks its orders (`on delete set null`) instead of failing.
- Saving an order takes its item quantities off `product_variants.quantity`, and removing items or deleting the order puts them back. The trigger on `order_items` does it. Items saved before stock tracking began have `stock_tracked = false` and never touch stock, and `save_order` keeps that flag when such an order is edited.
- An item's `sub_total` is stored, not recomputed from the product's current price. The dialog fills it in as price × quantity, and it can still be overridden for a discount. Deleting a product that is on an order fails at the DB, so `deleteProduct` checks first.
- Optimistic writes (deletes, mark invoice paid, order status steps) revert the row when they fail. A failed action only logs to the console. The order status step uses `setOrderStatusAction`, which updates only `order_status` so the items and their stock stay untouched.
- Delete prompts ("has 3 orders", "used by 5 transactions") read usage counts from the table rows, which the SQL summaries compute. Add the count to the row when adding a delete that the DB would reject.
